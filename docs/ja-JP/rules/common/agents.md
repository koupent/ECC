# Agent オーケストレーション

## 利用可能な Agent

`~/.claude/agents/` に配置:

| Agent | 目的 | 使用タイミング |
|-------|---------|-------------|
| planner | 実装計画 | 複雑な機能、リファクタリング |
| architect | システム設計 | アーキテクチャの意思決定 |
| tdd-guide | テスト駆動開発 | 新機能、バグ修正 |
| code-reviewer | コードレビュー | コード記述後 |
| security-reviewer | セキュリティ分析 | コミット前 |
| build-error-resolver | ビルドエラー修正 | ビルド失敗時 |
| e2e-runner | E2Eテスト | 重要なユーザーフロー |
| refactor-cleaner | デッドコードクリーンアップ | コードメンテナンス |
| doc-updater | ドキュメント | ドキュメント更新 |

## Agent 使用ポリシー

正本は `rules/common/agents.md` です。この文書はその翻訳です。

**適用範囲。** このポリシーは、本パックの他のすべてのルール文書にある「Xエージェントを使用する」
という手順を、その表現がどれほど断定的でも支配します。そうした手順はすべて「このポリシーが委任を
許可する場合に委任する」と読んでください。

**仕組み。** このルールは委任が有用な場面を説明するだけで、agent を自動的に起動しません。
ランタイムが自動起動する仕組みもありません。agent は、親モデルが利用可能な Agent または
Task ツールを呼び出し、その結果を回収したときにだけ動きます。

**期待。** そのツールが利用でき、より高優先度の指示が許可している場合は、委任するかどうかを
自分で判断してください。ユーザーからの個別の要求は必要ありません。

**優先順位。** system、ランタイムまたはハーネス、組織、ユーザーの高優先度指示は、常にこの
ルールに優先します。ハーネスが委任を制限している場合（例:「ユーザーが要求しない限り Agent
ツールを呼ばない」）は、ハーネスに従ってください。そのときこのルールは、どの観点を満たすべき
かを示すものであり、制限を上書きしてよいという許可ではありません。

委任ツールが利用でき、高優先度の指示が許可している場合:
1. 複雑な機能リクエスト - **planner** agent を検討
2. コード作成/変更直後 - **code-reviewer** agent を検討
3. バグ修正または新機能 - **tdd-guide** agent を検討
4. アーキテクチャの意思決定 - **architect** agent を検討

委任が利用できない、または禁止されている場合は、作業を親コンテキストに留め、同じ計画・
テスト・レビューのチェックリストをそのまま適用してください。ツールを呼び出して結果を回収して
いないのに agent が動いたと述べてはいけません。

## 並列タスク実行

並列 Task 実行は、本当に独立した操作に対して、ランタイムが委任を許可し、かつ親がターンを
終える前にすべての結果を回収できる場合にのみ使用してください。投げっぱなしの委任は禁止です:

```markdown
# 良い例: 並列実行
3つの agent を並列起動:
1. Agent 1: 認証モジュールのセキュリティ分析
2. Agent 2: キャッシュシステムのパフォーマンスレビュー
3. Agent 3: ユーティリティの型チェック

# 悪い例: 不要な逐次実行
最初に agent 1、次に agent 2、そして agent 3
```

## 多角的分析

複雑な問題には、委任が許可され観点が本当に独立している場合に、役割分担したサブ agent を検討:
- 事実レビュー担当
- シニアエンジニア
- セキュリティエキスパート
- 一貫性レビュー担当
- 冗長性チェック担当

委任が利用できない場合は、同じ観点を親コンテキストで個別のパスとして実行してください。差分
だけを見るレビューが見落とす欠陥（差分は1行でも手順全体の順序が誤っている場合など）を捕まえる
のは観点であり、agent はその手段にすぎません。
