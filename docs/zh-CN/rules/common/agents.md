# 智能体编排

## 可用智能体

位于 `~/.claude/agents/` 中：

| 代理 | 用途 | 使用时机 |
|-------|---------|-------------|
| planner | 实现规划 | 复杂功能、重构 |
| architect | 系统设计 | 架构决策 |
| tdd-guide | 测试驱动开发 | 新功能、错误修复 |
| code-reviewer | 代码审查 | 编写代码后 |
| security-reviewer | 安全分析 | 提交前 |
| build-error-resolver | 修复构建错误 | 构建失败时 |
| e2e-runner | 端到端测试 | 关键用户流程 |
| refactor-cleaner | 清理死代码 | 代码维护 |
| doc-updater | 文档 | 更新文档 |
| rust-reviewer | Rust 代码审查 | Rust 项目 |

## 智能体使用策略

`rules/common/agents.md` 是委派策略的正本；本文档是它的译文。

**适用范围。** 本策略管辖本规则包中其他所有规则文档里的每一条「使用 X 智能体」的步骤，无论该
步骤的措辞多么绝对。请把这类步骤一律读作「在本策略允许委派时才委派」。

**机制。** 本规则说明何时适合委派，但它不会自动启动智能体，运行时也不会自行启动。只有当父模型
调用可用的 Agent 或 Task 工具并回收其结果时，智能体才会运行。

**期望。** 当该工具可用且更高优先级的指令允许时，请自行判断是否委派。无需用户单独提出请求。

**优先级。** 系统、运行时或 harness、组织和用户的更高优先级指令始终优先于本规则。当 harness
限制委派时（例如「除非用户要求，否则不要调用 Agent 工具」），请遵循 harness。此时本规则说明的
是应覆盖哪些视角，而不是允许覆盖该限制。

当委派工具可用且更高优先级的指令允许使用时：

1. 复杂的功能请求 - 考虑 **planner** 智能体
2. 刚编写/修改的代码 - 考虑 **code-reviewer** 智能体
3. 错误修复或新功能 - 考虑 **tdd-guide** 智能体
4. 架构决策 - 考虑 **architect** 智能体

当委派不可用或被禁止时，请将工作保留在父上下文中，并直接套用同样的规划、测试与审查清单。在没有
调用工具并回收结果的情况下，绝不可声称智能体已运行。

## 并行任务执行

仅当运行时允许委派，且父模型能在结束本轮之前回收全部结果时，才对真正独立的操作使用并行任务执行。
禁止发出后不回收结果的委派：

```markdown
# 良好：并行执行
同时启动 3 个智能体：
1. 智能体 1：认证模块的安全分析
2. 智能体 2：缓存系统的性能审查
3. 智能体 3：工具类的类型检查

# 不良：不必要的顺序执行
先智能体 1，然后智能体 2，最后智能体 3

```

## 多视角分析

对于复杂问题，当允许委派且各视角确实相互独立时，可考虑使用拆分角色的子智能体：

* 事实审查员
* 高级工程师
* 安全专家
* 一致性审查员
* 冗余检查器

当委派不可用时，请在父上下文中以独立的多遍审查执行同样的视角。能够发现仅看 diff 的审查所遗漏
缺陷的是视角本身（例如 diff 只改动一行、但整个流程的步骤顺序有误）；智能体只是载体。
