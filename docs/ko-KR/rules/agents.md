# 에이전트 오케스트레이션

## 사용 가능한 에이전트

`~/.claude/agents/`에 위치:

| 에이전트 | 용도 | 사용 시점 |
|---------|------|----------|
| planner | 구현 계획 | 복잡한 기능, 리팩토링 |
| architect | 시스템 설계 | 아키텍처 의사결정 |
| tdd-guide | 테스트 주도 개발 | 새 기능, 버그 수정 |
| code-reviewer | 코드 리뷰 | 코드 작성 후 |
| security-reviewer | 보안 분석 | 커밋 전 |
| build-error-resolver | 빌드 에러 수정 | 빌드 실패 시 |
| e2e-runner | E2E 테스팅 | 핵심 사용자 흐름 |
| database-reviewer | 데이터베이스 스키마/쿼리 리뷰 | 스키마 설계, 쿼리 최적화 |
| go-reviewer | Go 코드 리뷰 | Go 코드 작성 또는 수정 후 |
| go-build-resolver | Go 빌드 에러 수정 | `go build` 또는 `go vet` 실패 시 |
| refactor-cleaner | 사용하지 않는 코드 정리 | 코드 유지보수 |
| doc-updater | 문서 관리 | 문서 업데이트 |

## 에이전트 사용 정책

위임 정책의 정본은 `rules/common/agents.md`이며, 이 문서는 그 번역본입니다.

**메커니즘.** 이 규칙은 위임이 유용한 상황을 설명할 뿐, 에이전트를 자동으로 실행하지 않으며
런타임이 스스로 실행하지도 않습니다. 에이전트는 상위 모델이 사용 가능한 Agent 또는 Task 도구를
호출하고 그 결과를 회수했을 때만 동작합니다.

**기대.** 해당 도구를 사용할 수 있고 더 높은 우선순위의 지시가 허용한다면, 위임 여부를 스스로
판단하십시오. 사용자의 별도 요청은 필요하지 않습니다.

**우선순위.** 시스템, 런타임 또는 하네스, 조직, 사용자의 더 높은 우선순위 지시가 항상 이 규칙에
우선합니다. 하네스가 위임을 제한하는 경우(예: "사용자가 요청하지 않는 한 Agent 도구를 호출하지
말 것)에는 하네스를 따르십시오. 그때 이 규칙은 어떤 관점을 충족해야 하는지를 알려줄 뿐, 제한을
무시해도 된다는 허가가 아닙니다.

위임 도구를 사용할 수 있고 더 높은 우선순위의 지시가 사용을 허용하는 경우:
1. 복잡한 기능 요청 - **planner** 에이전트 검토
2. 코드 작성/수정 직후 - **code-reviewer** 에이전트 검토
3. 버그 수정 또는 새 기능 - **tdd-guide** 에이전트 검토
4. 아키텍처 의사결정 - **architect** 에이전트 검토

위임이 불가능하거나 금지된 경우에는 작업을 상위 컨텍스트에 두고 동일한 계획, 테스트, 리뷰
체크리스트를 그대로 적용하십시오. 도구를 호출하고 결과를 회수하지 않았는데 에이전트가 실행되었다고
말해서는 안 됩니다.

## 병렬 Task 실행

병렬 Task 실행은 정말로 독립적인 작업에 대해, 런타임이 위임을 허용하고 상위 모델이 턴을 끝내기
전에 모든 결과를 회수할 수 있을 때만 사용하십시오. 결과를 회수하지 않는 위임은 금지됩니다:

```markdown
# 좋음: 병렬 실행
3개 에이전트를 병렬로 실행:
1. 에이전트 1: 인증 모듈 보안 분석
2. 에이전트 2: 캐시 시스템 성능 리뷰
3. 에이전트 3: 유틸리티 타입 검사

# 나쁨: 불필요하게 순차 실행
먼저 에이전트 1, 그다음 에이전트 2, 그다음 에이전트 3
```

## 다중 관점 분석

복잡한 문제에는, 위임이 허용되고 관점이 실제로 독립적일 때 역할 분리 서브에이전트를 검토:
- 사실 검증 리뷰어
- 시니어 엔지니어
- 보안 전문가
- 일관성 검토자
- 중복 검사자

위임이 불가능한 경우에는 동일한 관점을 상위 컨텍스트에서 개별 패스로 수행하십시오. diff만 보는
리뷰가 놓치는 결함(예: diff는 한 줄이지만 절차 전체의 순서가 잘못된 경우)을 잡아내는 것은
관점이며, 에이전트는 그 수단일 뿐입니다.
